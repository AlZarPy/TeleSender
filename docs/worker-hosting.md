# Где держать воркер рассылки: компьютер или сервер

Сравнение двух вариантов размещения SenderX (воркер + база + сессии аккаунтов).
Дата: 11 ноября 2026. Сервер: `213.171.29.117` (cloud.ru, `user1`), Ubuntu, второй Hermes.

## Коротко

| | Компьютер (сейчас) | Сервер |
|---|---|---|
| Готовность | работает | нужно перенести (2–3 часа) |
| Работает ночью | нет, если ПК спит | да |
| Стоимость | 0 | уже оплачен |
| Отладка | простая | через SSH и логи |
| Риск потерять данные | диск ПК | диск ВМ + бэкап |

## Подробное сравнение

| Критерий | Компьютер | Сервер |
|---|---|---|
| **Время работы** | пока включён; спящий ноутбук останавливает волну | 24/7, `systemd` + `linger` |
| **Скорость рассылки** | 5 000 за 15 дней при непрерывной работе | 5 000 за 12–13 дней, простоев нет |
| **Влияние на вашу работу** | мешает: воркер и вы делите машину, вентилятор, батарея | не мешает, вы работаете как обычно |
| **IP аккаунтов** | через прокси (португальские адреса) | **те же прокси** — переезд не меняет IP аккаунта |
| **Зависимость от сети** | ваша домашняя сеть + прокси | сеть дата-центра + прокси |
| **Перезапуск после сбоя** | вручную: закрыли окно — воркер умер | `Restart=always`, поднимется сам |
| **Доступ к панели** | локально, мгновенно | через SSH-туннель (`ssh -L 8099:127.0.0.1:8099`) |
| **Безопасность ключей** | файлы на вашем диске | ключи на сервере: нужен SSH-ключ, закрытый порт, без пароля |
| **Бэкап** | диск ПК, риск при поломке | снимок ВМ + выгрузка `panel.db` раз в сутки |
| **Отладка ошибок** | видно всё сразу, консоль рядом | логи `journalctl`, чуть медленнее |
| **Обновление кода** | `git pull` локально | `git pull` + `systemctl restart` |
| **Стоимость** | 0 ₽ | ВМ уже оплачена (Telegram-бот там живёт) |
| **Риск для бота Hermes** | нет связи | воркер и бот делят ВМ: при падении одного второй живёт, если раздельные сервисы |
| **Юридически** (152-ФЗ) | данные в вашей квартире | данные в РФ (cloud.ru), это плюс |

## Что именно переносится

| Объект | Размер / вид | Как |
|---|---|---|
| Код проекта | ~2 МБ | `git clone` на сервере |
| `.session` файлы аккаунтов | 22 файла × 256 байт | `scp`, права 600 |
| `panel.db` | 224 КБ | `scp`, затем ежедневный бэкап |
| `config.txt` | api_id/api_hash + список сессий | `scp` |
| `proxies.txt` | 21 строка | `scp` |
| `.env` | ключи RouterAI, пароль панели | **вручную**, не через git |
| Python 3.12 + зависимости | venv | `python -m venv`, `pip install -r requirements.txt` |
| systemd-юнит | `senderx-worker.service` | уже есть в `deploy/systemd/` |

## Риски и как их снимаем

| Риск | Снижение |
|---|---|
| Аккаунты «заметят» смену окружения | IP не меняется: трафик идёт через те же прокси, меняется только машина-отправитель |
| Одновременный запуск воркера в двух местах | перед стартом на сервере остановить локальный; в базе есть heartbeat, второй воркер виден |
| Утечка сессий | права 600 на файлы, порт панели только на 127.0.0.1, SSH по ключу |
| Падение сервера | `Restart=always`, плюс ежедневный снимок `panel.db` к вам на диск |
| Потеря доступа к панели | SSH-туннель, либо временно поднять локальную копию на бэкапе базы |

## План переноса (если решим)

1. Остановить локальный воркер, сохранить `panel.db`.
2. На сервере: `git clone`, venv, зависимости.
3. Скопировать сессии, `config.txt`, `proxies.txt`, `panel.db`, `.env`.
4. Прогнать `python -m panel.worker --dry-run` — проверка без отправок.
5. Включить `senderx-worker.service`, проверить heartbeat и `/healthz`.
6. Панель оставить локально, подключать через SSH-туннель.
7. Крон на сервере: ежедневная выгрузка `panel.db` к вам.

Откат: остановить службу на сервере, вернуть локальный воркер — база одна и та же, потерь нет.

## Вывод

Для цели «5 000 сообщений без пауз» сервер выигрывает по всем рабочим параметрам, кроме удобства отладки.
Компьютер оставить смысл только для правок кода и просмотра панели.
