# База фактов и проверка чисел · спецификация

Задача: модель отвечает в диалоге только теми числами, датами и именами, которые есть
в источнике. Всё остальное — блокируется до отправки.

## 1. Почему не «просто промпт»

Факты в системном промпте работают до первого длинного ответа: 30 реплик памяти,
шесть карточек программы, и модель начинает складывать числа из головы. Типичные
ошибки, которые видит получатель:

- «13 ноября в 14:00» вместо 15:00;
- «39 мастер-классов в 6 залах» вместо 5;
- выдуманный наставник с правдоподобной фамилией;
- «регистрация закрыта» — модель достроила логику, которой нет;
- «участие 5000 ₽» — смешала бесплатное участие с платными школами.

Одна такая фраза в холодном диалоге стоит дороже десяти отправленных сообщений.

## 2. Карточка — единица знания

Карточка это один факт, а не страница текста. Правило: **одна карточка = один вопрос,
на который человек может спросить.**

| Поле | Что содержит |
|---|---|
| `id` | короткий код (`event_date`, `school_neuro`) |
| `topic` | группа: событие, программа, школы, наставники, логистика, регистрация, возражения |
| `title` | формулировка вопроса («когда и во сколько») |
| `body` | ответ в 1–3 предложениях, только проверенные факты |
| `facts` | машинный список: числа, даты, имена — для сверки (`15:00`, `13.11.2026`, `39`, `Илья Дрозд`) |
| `keywords` | слова для поиска, включая синонимы и опечатки («во сколько», «начало», «time») |
| `source` | откуда взято: URL лендинга, дата снятия, кто подтвердил |
| `updated_at` | когда проверено |
| `sensitive` | 1, если карточку нельзя пересказывать вольно (цены, гарантии, юридика) |

Почему `facts` отдельно: текст карточки идёт в промпт, а `facts` — в проверку.
Модель может переписать ответ своими словами, но число должно совпасть с `facts`
посимвольно после нормализации.

## 3. Состав базы под мероприятие (50–80 карточек)

| Группа | Примеры карточек |
|---|---|
| Событие | дата и время, адрес с подъездом, вход/выход, бесплатность, 41-й поток |
| Программа | 39 мастер-классов, 5 залов, расписание по часам, две смены наставников |
| Школы | шесть школ с ведущими, тема каждой, как выбрать |
| Наставничество | 3 месяца, группа 8–10, раз в неделю, что разбирают |
| Направления ИИ | Vibe coding, Neuro-seller, Content factory, AI assistant |
| Логистика | как добраться, парковка, схема залов, что взять |
| Регистрация | ссылка, нужен ли паспорт, можно ли без регистрации |
| Возражения | «далеко», «нет времени», «не моя тема», «а это точно бесплатно» |
| Границы | чего мы не обещаем (трудоустройство, рост выручки, места) |

Группа «Границы» обязательна: это ответы-запреты, по ним модель понимает, где молчать.

## 4. Схема SQLite + FTS5

```sql
CREATE TABLE facts (
    id         TEXT PRIMARY KEY,
    topic      TEXT NOT NULL,
    title      TEXT NOT NULL,
    body       TEXT NOT NULL,
    fact_list  TEXT NOT NULL DEFAULT '',   -- через \n: 15:00, 39, Илья Дрозд
    source     TEXT NOT NULL DEFAULT '',
    sensitive  INTEGER NOT NULL DEFAULT 0,
    updated_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE VIRTUAL TABLE facts_fts USING fts5(
    title, body, keywords,
    content='', tokenize='unicode61'
);
```

`content=''` — внешнее содержимое: храним текст только в `facts`, FTS держит индекс.
Токенайзер `unicode61` нормально режет кириллицу.

## 5. Поиск: 2–3 карточки, а не весь корпус

```
запрос = последняя реплика человека (+ 1–2 предыдущие, если короткая)
→ FTS5 MATCH по keywords/title/body, bm25, top 3
→ если пусто: поиск по topic из классификатора (расписание/школы/логистика)
→ если пусто и там: карточка «границы» + ответ «уточню и напишу»
```

В промпт кладётся не больше 3 карточек: больше — модель начинает смешивать факты
из разных тем. Плюс всегда одна карточка «границы».

## 6. Проверка после генерации

Алгоритм на каждый ответ, до отправки:

1. **Извлечь из ответа все числа, даты, время, имена собственные.**
   - числа: `\d+(?:[.,]\d+)?`
   - время: `\b\d{1,2}[:.]\d{2}\b`
   - даты: `\b\d{1,2}\s+(январ|феврал|март|апрел|ма[йя]|июн|июл|август|сентябр|октябр|ноябр|декабр)`
   - имена: слова с заглавной буквы, кроме начала предложения и названий школы/города из белого списка
2. **Нормализовать** (15:00 = 15.00 = «три часа дня» → 15:00; 13.11.2026 = 13 ноября).
3. **Сверить с объединённым `fact_list` карточек, попавших в промпт.**
4. Если число/имя не найдено — **не отправлять**.

Разрешённые исключения (белый список): «3 месяца», «8–10 человек», «второй этаж»,
если они есть в карточках; слова-связки без фактов («пару минут», «несколько»).

## 7. Что делать при провале

| Попытка | Действие |
|---|---|
| 1 | перегенерировать с указанием: «используй только эти факты: …», temperature 0.3 |
| 2 | отправить шаблонный ответ из правил (announce/explain), без модели |
| 3 | молчать, записать в журнал `fact_block` с текстом ответа и расхождением |

Каждый блок пишется в события: `fact_block`, `fact_regenerated`, `fact_fallback`.
Через неделю это готовый список дыр в базе: если блоков много по теме «расписание» —
значит карточки неполные, а не модель плохая.

## 8. Чувствительные карточки

`sensitive=1` — цены, условия участия, юридические формулировки, гарантии.
Правило: такие карточки нельзя пересказывать, только цитировать дословно
(или отвечать шаблоном). Проверка для них строже: расхождение хотя бы в одном
числе — сразу шаблон, без перегенерации.

## 9. Стоимость и скорость

- поиск по FTS5: единицы миллисекунд, бесплатно;
- проверка регулярками: бесплатно, ~1 мс;
- лишний вызов модели только при провале (по нашей статистике — 5–10% ответов);
- карточки в промпте: 300–800 токенов вместо 3000 у полного корпуса, то есть дешевле
  и точнее, чем «залить всё».

## 10. Порядок работ

1. Выгрузить карточки с лендинга и из чата школы (сейчас — 40–50 штук).
2. Заполнить `facts` и `source` у каждой; чего нет — помечать `sensitive=0` и «уточнить».
3. Создать FTS5-индекс, прогнать 20 живых вопросов, глазами проверить top-3.
4. Подключить в `salesperson.compose`: поиск → карточки в промпт.
5. Включить проверку чисел в режиме «только журнал» на сутки (не блокировать),
   посмотреть, сколько ложных срабатываний.
6. Включить блокировку. Через неделю — разбор `fact_block` и пополнение базы.

## 11. Чего не делать

- не грузить в RAG весь лендинг целиком: в ответ попадут маркетинговые фразы;
- не давать модели больше 3 карточек за раз;
- не включать блокировку без периода «только журнал» — ложные срабатывания
  на «8–10 человек» и «второй этаж» съедят живые ответы;
- не хранить в карточках непроверенные обещания («рост выручки в 2 раза»):
  проверка чисел их не поймает, а жалобу они принесут.
